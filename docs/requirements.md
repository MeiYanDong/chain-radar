# Chain Radar 需求文档纲领

> 维护规则：本文档描述产品需求和用户判断，只能由用户主动更新。Agent 可以阅读、引用、提出修改建议，但不要在没有明确授权时直接改动本文档。

## 1. 产品一句话

Chain Radar 是一个帮助普通用户观察 Virtuals Degen 交易赛和相关代币机会的工具。

它不替用户做交易，也不承诺预测价格；它的价值是把分散在网页、链上数据和交易赛数据里的信号整理出来，让用户更早看见值得关注的变化。

## 2. 用户是谁

核心用户是一个不写代码、但愿意用 AI 辅助自己做投资研究的普通人。

他可能是一个在校大学生小白：

- 看得懂收益、亏损、成本、涨跌，但不想研究复杂技术细节。
- 愿意自己判断，而不是完全听 KOL 喊单。
- 想用更低门槛看懂链上和交易赛数据。
- 不想一直盯着网页刷新，希望关键变化发生时被提醒。

## 3. 用户遇到的问题

Virtuals Degen 这类活动里，信息变化很快，但普通用户看到的是零散页面：

- 某个 Agent 当前赚不赚钱。
- Pot 跟单资金有没有明显变化。
- 大户的持仓成本大概在哪里。
- 价格变化是否已经反映了这些信息。
- 什么时候只是噪音，什么时候可能是值得观察的信号。

这些数据原本是公开的，但没有被整理成一个普通人能快速理解的视图。

用户真正需要的不是更多数字，而是更清楚地回答：

> 现在有没有一个值得我打开来看、继续研究、甚至准备行动的机会？

## 4. 产品目标

Chain Radar 的目标是成为一个“机会雷达”：

- 帮用户更快发现 Virtuals Degen 交易赛里的强弱变化。
- 帮用户看到 Agent 赚钱或亏钱是否正在扩大。
- 在需要时保留大户筹码成本作为辅助参考，但当前不把它作为主线维护。
- 在重要变化发生时主动提醒用户，而不是让用户一直盯盘。
- 用普通语言解释数据含义，让不会写代码的人也能看懂。

## 5. 当前产品阶段

项目已经不是从零开始，目前处于 Phase 2 之后的迭代阶段。

建议按以下历史阶段理解：

- Phase 0：想法验证
  - 从一个问题开始：大户们的成本到底是多少？
  - 目标是验证链上数据能不能帮助判断入场位置。

- Phase 1：大户成本分析 Dashboard
  - 展示代币持有人榜单、买入成本、未实现收益、已实现收益和地址详情。
  - 重点是看清大户筹码分布。

- Phase 2：Virtuals Degen Pot Monitor
  - 从单个代币的大户分析，扩展到观察交易赛中 10 个 Agent 的 Pot 表现。
  - 重点是监控 Live P&L 和关键变化，并通过飞书提醒用户。

- Phase 2.1：云服务器同步与常驻运行
  - 当前重点不是继续增加复杂功能，而是让工具稳定运行、提醒可靠、部署到云服务器。

- Phase 2.2：提醒阈值重新设计
  - 后续重点是重新设计 Pot Monitor 的提醒规则，减少误报，让每条提醒更值得用户打开看。

## 6. 当前最重要的需求

当前优先级最高的是：

> 让 Pot Monitor 可以稳定地在云服务器上运行，并在关键 P&L 变化时可靠提醒用户。

这件事成功以后，用户不需要开着本机终端，也不需要一直盯网页。

## 7. 当前核心能力

### 7.1 大户成本分析（暂停维护）

用户可以查看某个代币的大户持仓情况：

- 谁持有最多。
- 大概花了多少钱买入。
- 平均买入价对应什么市值。
- 当前是浮盈还是浮亏。
- 是否已经卖出并产生已实现收益。

这部分能力适合回答：

> 现在价格附近，大户是赚钱很多、亏损很多，还是接近成本线？

当前阶段暂不继续维护大户成本分析。它保留为历史能力和辅助视图，不作为 Phase 2.1 的主流程。

### 7.2 Pot Monitor

用户可以观察 Virtuals Degen 交易赛里的 Agent 表现：

- 哪些 Agent 当前赚钱。
- 哪些 Agent 当前亏钱。
- Live P&L 是否突破关键阶梯。
- 15 分钟或 1 小时内是否出现明显变化。
- 是否需要通过飞书提醒用户打开页面进一步查看。

这部分能力适合回答：

> 哪个 Agent 的表现正在快速变化，我是不是应该马上看一眼？

## 8. 提醒的产品原则

提醒不是越多越好。

好的提醒应该满足：

- 变化足够大，值得用户打开看。
- 不因为临时错误数据误报。
- 不因为程序重启重复轰炸。
- 能告诉用户“发生了什么”，而不是只丢一个数字。
- 不直接告诉用户买或卖，只提示“值得关注”。

后续重新设计 Pot Monitor 阈值时，思路来自四个来源：

- 用户注意力：提醒应该少而有用，不能把飞书变成噪音。
- 历史波动：用已经记录下来的 P&L 快照观察正常波动范围，区分普通波动和异常变化。
- 行动价值：只有当变化可能让用户打开页面继续判断时，才值得提醒。
- 数据质量：规则必须先过滤空数据、旧数据、重启状态和 API 抖动，避免因为假数据误报。

因此，后续阈值不应该只依赖固定的 `$2k`、`$5k` 这类数字。更合理的方向是把绝对金额、相对本金比例、短时间变化、赛季阶段和冷却机制组合起来，让提醒更接近“值得关注的机会”，而不是简单的数字越线。

提醒阈值和评分函数要分开：

```text
提醒阈值 = 用于决定什么时候通知用户。

评分函数 = 用于判断信号强弱和仓位梯度。
```

评分应尽量使用连续函数，避免在 `$2k`、`$5k` 这类临界值附近出现不合理跳变。

## 9. 非目标

Chain Radar 暂时不做这些事：

- 不自动交易。
- 不托管用户资金。
- 不直接给买卖指令。
- 不承诺预测币价。
- 不追求专业量化系统的复杂度。
- 不把所有链上数据都做成大而全平台。
- 不为了好看而牺牲提醒稳定性。

## 10. 成功标准

当前阶段的成功标准：

- 用户不用开本机终端，云服务器也能持续运行 Pot Monitor。
- 关键 P&L 变化能稳定触发飞书提醒。
- 提醒不会因为空数据、旧数据、重启状态而频繁误报。
- 用户收到提醒后，能看懂发生了什么。
- 用户能通过网页查看当前 Pot 数据；大户成本分析暂时只作为辅助历史能力保留。
- 新 Agent 接手项目时，能先读文档理解产品目标，而不是直接钻进代码。

## 11. 文档协作规则

- 本文档是需求纲领，只描述“为什么做、给谁用、解决什么问题”。
- Plan 文档应该站在产品路线图角度，不写技术细节。
- Todo 文档应该描述当前要完成的产品事项，不写代码流水账。
- 技术细节、命令、文件改动、部署步骤，应放到阶段子 plan / 子 todo 或运行文档里。
- 如果 Agent 发现需求和代码实现不一致，应先向用户说明，不要直接改本文档。

## 12. 当前已确认

- 当前阶段命名为 `Phase 2.1：云服务器同步与常驻运行`。
- 大户成本分析暂停维护，只保留为历史能力和辅助视图。
- Pot Monitor 是当前主线。
- Pot Monitor 的提醒阈值后续会重新设计，当前阶段先保证稳定运行。
